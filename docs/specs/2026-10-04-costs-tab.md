# Costs Dashboard Tab

- **Date:** 2026-10-04
- **Status:** Approved for planning (user design approved 2026-10-04; revised 2026-10-04 after the artifact-gate BLOCK — reviewer-verified facts and user resolutions R1–R6 folded in)
- **Scope:** new `#/costs` frontend tab (period selector, per-provider KPIs, cost-share donut, daily stacked bars, per-model table) plus one new backend endpoint `GET /api/cost-series`
- **Binding constraints:** stdlib only, SQL parameter binding, files ≤ ~400 lines, tests fully offline, no changes to `db.py` / `scanner.py` / importers

---

## Objective

The dashboard has per-model cost data (`/api/by-model`) but no cost-first view: users
cannot see spend per provider, cost trend over time, or which models dominate spend.
This spec adds a "costs" tab that aggregates the existing stored-first cost data by
**provider** and by **day**, with a per-model table, behind one new read-only endpoint.
All cost aggregation follows the stored-first preference, implemented in the new
endpoint's own merge (`pricing.cost_for` is reused; the 0-coercing
`queries.merge_model_group_cost` is NOT reused unchanged — see §5); the provider
split happens entirely in the frontend.

## Context

- **Frontend** is a hash-routing SPA: routes are registered in the `ROUTES` object in
  `web/app.js` (~140 lines), each route is a module under `web/routes/*.js`, and
  chart rendering goes through themed ECharts wrappers (`barChart`,
  `stackedBarChart`, `donutChart`, `lineChart`) in `web/charts.js`. ECharts is
  vendored at `web/echarts.min.js`; there is no build step. Existing tabs:
  overview, prompts, sessions, projects, skills, tips, settings.
- **Pattern sources:** `web/routes/overview.js` holds the KPI-card / donut layout
  pattern to follow; `web/routes/settings.js` holds the escape-XSS rendering
  pattern (`esc()`-style helper) to follow for every dynamic string.
- **Existing data:** `GET /api/by-model?since=&until=` returns per-model rows
  `{model, turns, input_tokens, output_tokens, cache_read_tokens,
  cache_create_5m_tokens, cache_create_1h_tokens, stored_cost, null_* token
  totals, cost_usd, cost_estimated}` — `cost_usd` is stored-first (native
  `cost_usd` when `> 0`, else estimated from models.dev rates; an unpriceable
  model's group arrives as `cost_usd: 0` — the merge coerces). There is no
  daily (per-date) cost series endpoint today; the new `/api/cost-series`
  (§5) is this tab's ONLY data source — the tab never calls `/api/by-model`,
  and `/api/by-model` stays untouched for the other tabs.
- **Backend:** cost aggregation queries live in `token_dashboard/queries.py`
  (137 lines) with the stored-first merge logic; HTTP handlers live in
  `token_dashboard/server.py` (291 lines). Reviewer-verified facts: there is
  NO existing `since`/`until` validation or 400 pattern for GET handlers
  (params pass straight through; `_send_error(400)` exists only for POST
  bodies), so this endpoint's validation is NEW code; `merge_model_group_cost`
  coerces an unpriceable group's cost to `0` (never `null`). Module line
  counts are well under the ~400 limit.
- **Model id convention:** models are stored as bare ids (`glm-5.3-flash`,
  `kimi-k2.7-code`) for opencode v2 rows, but provider-prefixed ids
  (`ollama-cloud/kimi-k2.7-code`) may also appear — the provider derivation in
  Design Decisions §4 handles both. Reviewer-verified: existing model-grouping
  queries (`model_breakdown`) apply `COALESCE(model, 'unknown')`, so NULL
  models reach the API as the literal string `'unknown'`, never SQL NULL.
- **Range and day-bucketing facts (reviewer-verified):** `_range_clause` treats
  `until` as EXCLUSIVE (`col < ?`). The only existing daily query
  (`daily_token_breakdown`, `db.py`) buckets days by `substr(timestamp, 1, 10)`
  — a UTC string slice. This spec KEEPS the exclusive `until` and CHOOSES
  local-day bucketing over the UTC slice (see §2 and §5).
- **Cost semantics (unchanged by this spec):** costs are an "API-rate equivalent
  cost" proxy — stored native cost when > 0, otherwise models.dev-rate estimate.
  Subscription/flat providers reporting `0` fall back to the estimate (user
  decision 2026-10-03, see the v2 storage spec §3).

## Design Decisions

User-approved 2026-10-04; revised 2026-10-04 after the artifact-gate BLOCK
(user resolutions R1–R6 folded in) — decisions 1–7 are binding.

### 1. Route: one file, one ROUTES entry (binding)

- New tab at hash `#/costs`, implemented in the NEW file `web/routes/costs.js`
  (~180–220 lines), plus exactly ONE new line in `web/app.js`'s `ROUTES` object
  (same shape as the existing entries). Menu label: `costs`.
- `web/app.js` stays ~140 lines total (the single added entry is the only edit).
- The route module follows the existing module contract: export a render/init
  function receiving the route container, fetch its data, render, and register
  chart instances the same way other routes do.

### 2. Period selector (binding)

- Top of the page: period buttons **7d / 30d / 90d / all** plus a **custom range**
  control (two date inputs `since` / `until`).
- Period → `since`/`until` query params with the repo's actual range semantics
  (reviewer-verified): `since` inclusive, **`until` EXCLUSIVE** (matching
  `_range_clause`, which filters `col < ?`). `7d`/`30d`/`90d` compute
  `since = today − N days`, `until` omitted. `all` omits both.
- **Custom range:** the user picks an INCLUSIVE end day in the UI; the frontend
  sends `until = end day + 1 day` so the exclusive filter still covers the
  picked day. Both params are emitted as full ISO datetimes (`toISOString()`),
  matching what the existing routes send.
- **Default: 30d.** Changing the period re-fetches and re-renders (all four
  sections) with the new params. Custom range applies on explicit user action
  (apply button or change event), not per keystroke.

### 3. Layout, in order (binding)

1. **KPI cards per provider** — for each provider present in the period:
   - total cost in period (sum of row `cost_usd` across the provider's
     `(date, model)` rows, excluding null-cost rows — EC-4);
   - % of total period cost (across all providers);
   - monthly extrapolation = avg cost/day × 30, where avg cost/day =
     total period cost / number of days in the period (for `all`, use the
     actual span in days between first and last activity date, minimum 1).
2. **Donut chart** of cost share per provider (existing `donutChart` wrapper,
   same usage as `overview.js`).
3. **Daily stacked bar chart** of cost per provider per day (existing
   `stackedBarChart` wrapper) fed by the NEW `/api/cost-series` endpoint
   (§5) — one stack series per provider, one bar per day.
4. **Per-model table** — columns: model, provider, turns, input tokens, output
   tokens, cache tokens (read + create, one column or two adjacent — implementer
   follows the table conventions of an existing route), cost USD, % of total
   cost, and an **"est." badge** on the cost cell when the row's `cost_estimated`
   is true (aggregating the endpoint's daily rows by model client-side, a
   model's `cost_estimated` is the OR over its contributing rows). Sortable
   columns, **default sort: cost descending**. Footer row with
   totals (turns, tokens, cost; % column footer shows 100%).

**All four sections are fed by the new `/api/cost-series` endpoint ALONE** —
the tab never fetches `/api/by-model` (that endpoint stays untouched for the
other tabs). The frontend aggregates the endpoint's `(date, model)` rows three
ways: by **provider** (KPI cards, donut), by **date** (stacked bar), and by
**model** (table).

### 4. Provider derivation (frontend only) (binding)

Provider is derived in the FRONTEND from the model string, in this order:

1. The literal string `'unknown'` — what `COALESCE(model, 'unknown')` delivers
   for NULL models — maps to the `unknown` bucket FIRST, before any other
   rule (it must never fall through to `other`).
2. If the model string contains `/`, provider = `model.split('/')[0]`
   (e.g. `ollama-cloud/kimi-k2.7-code` → `ollama-cloud`).
3. Else, prefix mapping on the bare id (first matching prefix wins, longest
   sensible match):

   | Model prefix | Provider |
   |---|---|
   | `claude*` | `anthropic` |
   | `gemini*` | `google` |
   | `qwen*` | `alibaba` |
   | `deepseek*` | `deepseek` |
   | `gpt*`, `o3*` | `openai` |
   | `glm*` | `zhipu` |
   | `kimi*` | `moonshot` |

4. Unmatched non-empty model → `other`.
5. Empty / null / missing model (defensive — the backend already COALESCEs)
   → `unknown`.

The mapping table lives as a small ordered array of `[prefix, provider]` pairs
in `web/routes/costs.js` (no backend change, no config file).

### 5. New endpoint `GET /api/cost-series` (binding)

- **Backend function** `cost_series(since, until)` in
  `token_dashboard/queries.py`: returns daily rows grouped by
  `(date, model)` with:
  - `date` = `date(timestamp, 'localtime')` (local-day string `YYYY-MM-DD`).
    This intentionally DIFFERS from `/api/daily`'s `substr(timestamp, 1, 10)`
    UTC slice: the costs tab is a spend view aligned to the user's local day
    (user resolution R3). Do NOT adopt the `substr` convention.
  - `model` = `COALESCE(model, 'unknown')` — the same NULL handling as
    `model_breakdown`; NULL models arrive as the string `'unknown'`, never
    SQL NULL (user resolution R4).
  - `turns` (the same aggregate expression `model_breakdown` uses — cheap in a
    `GROUP BY`; included per user resolution R2) and the token sums
    (`input_tokens`, `output_tokens`, `cache_read_tokens`,
    `cache_create_5m_tokens`, `cache_create_1h_tokens`);
  - the stored/estimated cost split as merge INPUTS (the handler merges):
    `stored_cost = COALESCE(SUM(cost_usd), 0)` plus `null_*` token totals
    restricted to rows with `cost_usd IS NULL OR cost_usd = 0`, exactly like
    the existing aggregation functions in `queries.py`.
  - Range: `since` inclusive, `until` EXCLUSIVE — reuse `_range_clause`
    verbatim (parameters bound with `?`).
- **Handler** `GET /api/cost-series?since=&until=` in
  `token_dashboard/server.py`:
  - **NEW validation** (reviewer-verified: there is no existing GET-handler
    `since`/`until` validation to reuse): each present value must be
    `YYYY-MM-DD` or a full ISO-8601 datetime, validated with
    `datetime.fromisoformat`; a `YYYY-MM-DD` value is normalized to midnight
    of that day. Invalid values → **400** with a plain-text error body (the
    `_send_error(400)` output style). `since >= until` → **400**. Missing
    params → no validation, no range filter (all data). Both wire formats are
    accepted (user resolution R6); the frontend emits full ISO datetimes.
  - **Own null-preserving merge** (user resolution R2 — NOT
    `merge_model_group_cost` unchanged, which coerces unpriceable cost to
    `0`): the handler may reuse `pricing.cost_for` and computes each
    `(date, model)` row as:
    - `cost_usd = stored_cost` when `stored_cost > 0` (stored data is
      authoritative for the group);
    - else `cost_usd = cost_for(model, null-row tokens).usd`, with
      `cost_estimated: true`;
    - **unpriced case:** when `stored_cost == 0` AND `cost_for(...).usd is
      None` → `"cost_usd": null, "cost_estimated": true` — the unpriced
      marker the frontend renders as `—` (AC-20). Unlike `/api/by-model`'s
      additive merge, a group with both stored and computed parts reports the
      stored cost only (preference, not sum).
  - Response JSON: `{"rows": [{date, model, turns, input_tokens,
    output_tokens, cache_read_tokens, cache_create_5m_tokens,
    cache_create_1h_tokens, cost_usd, cost_estimated}, ...]}` — `cost_usd` is
    nullable; no `stored_cost` or `null_*` diagnostics leak to the wire.
- **`since >= until`** is rejected with 400 (NEW rule — no existing GET rule).
- **Provider split happens in the FRONTEND** — the backend never groups by
  provider. This keeps `queries.py` free of provider logic and lets the
  provider mapping evolve without backend changes.
- **No changes** to `db.py`, `scanner.py`, or importers. `queries.py` and
  `server.py` both stay under ~400 lines.

### 6. Cost semantics and display rules (binding)

- Costs remain stored-first; the tab presents them as an "API-rate equivalent
  cost" proxy. The `est.` badge on estimated rows makes this explicit; the
  empty/period footer also carries a one-line note (see Edge Cases EC-5).
- A model with no rate arrives from `/api/cost-series` with `cost_usd: null`
  (the §5 null-preserving merge — reachable, unlike `/api/by-model`'s coerced
  `0`). It is displayed with `—` in its cost cell, is **excluded from all cost
  aggregates** (KPIs, donut, extrapolation, stacked bar, footer cost total),
  and is **noted in the table footer** ("N models without rate — excluded
  from cost totals").
- Zero-cost models (computed cost exactly `0`) are NOT null: they display
  `$0.00` and are included in totals (they contribute 0).

### 7. Tests (binding)

- `tests/test_queries.py`: `cost_series` tests — empty period (no rows);
  stored+estimated mix exposing the merge inputs (`stored_cost` + `null_*`
  sums); NULL-model rows grouped under the STRING `'unknown'` (COALESCE);
  LOCAL-midnight date bucketing (messages around local midnight land on
  different `YYYY-MM-DD` values).
- `tests/test_server.py`: `/api/cost-series` handler tests — valid dates (both
  `YYYY-MM-DD` and ISO datetime forms) return rows with the documented fields
  and the null-preserving merge applied; invalid dates → 400; `since >= until`
  → 400; unpriceable group → `cost_usd: null`, `cost_estimated: true`.
- **Frontend has no JS test framework** (project convention): `costs.js` is
  verified by manual checks (AC-F manual items) plus code review only. No new
  JS tooling is introduced.

## Conventions

- **Stdlib only** — no new JS libraries, no npm, no build step; frontend edits
  are direct file edits under `web/`. No new Python dependencies.
- **SQL parameter binding ALWAYS** — `?` placeholders for `since`/`until` and
  any data value; f-strings only for fixed internal SQL fragments.
- **Files ≤ ~400 lines, one responsibility**: `web/routes/costs.js` owns the
  whole costs view (~180–220 lines); `queries.py` gains only the daily-series
  query; `server.py` gains only the handler; `db.py`, importers and scanner
  are untouched.
- **Hash-route pattern**: module + one `ROUTES` entry, matching the existing
  route modules' structure and naming.
- **Escape rendering**: the `settings.js` escape pattern for ALL dynamic text
  in `costs.js`.
- **Chart wrappers**: use `donutChart` and `stackedBarChart` from
  `web/charts.js` — never instantiate `echarts` directly in the route.
- **English** for code, identifiers, comments, and docs.
- **Tests**: `unittest.TestCase` only, explicit temp-dir paths, no network, no
  env patching; fixtures follow the existing `tests/fixtures/` conventions.

## Edge Cases

1. **Empty period** (no messages in range, e.g. a custom range before any
   activity): `/api/cost-series` returns `{"rows": []}` (the tab's only data
   source); the view shows a friendly empty state ("No cost data in this
   period") in place of KPI cards, donut, and charts — not zeros, not blank
   sections. **(manual)**
2. **Null or empty model string**: `cost_series` applies
   `COALESCE(model, 'unknown')` (same as `model_breakdown`), so rows group
   under the STRING `'unknown'` — never SQL NULL. The frontend
   `deriveProvider` special-cases the literal `'unknown'` → `unknown` bucket
   BEFORE the prefix rules (it must never fall through to `other`). The KPI
   card / donut slice label reads `unknown`. Never crashes, never renders
   `null` into the DOM. An empty-string model (defensive, if any exist) also
   maps to `unknown`.
3. **Invalid custom dates** (values `datetime.fromisoformat` rejects, or
   `since >= until`): the NEW handler validation (§5) returns 400; the
   frontend keeps the last valid render and shows a brief
   inline error message near the custom range control. No request storm (one
   request per apply action).
4. **Model with no rate** (`cost_usd: null` from the §5 null-preserving merge —
   the handler does NOT coerce to `0`): cost cell shows
   `—`, no `est.` badge, excluded from all cost aggregates (KPI, donut,
   extrapolation, stacked bar, footer totals), and the table footer counts
   these models ("N models without rate — excluded from cost totals").
5. **All cost rows estimated / all stored / mixed**: the merge logic (AC-10)
   already handles the split; the UI shows `est.` badges per row where
   `cost_estimated` is true. A period that is 100% stored-cost (no `est.`
   badges) and a period that is 100% estimated (every row badged) both render
   correctly.
6. **Provider with stored cost = 0 across the period** (subscription
   providers, e.g. `ollama-cloud`): per the > 0 preference rule those rows fall
   back to the computed estimate, so the provider still shows a non-zero
   estimated cost — expected, and the `est.` badges make it explicit.
7. **Day with messages but all cost `null`**: the stacked bar shows no bar for
   that day (or a zero-height bar — either is acceptable as long as no NaN is
   rendered and the day is present in the axis if other providers have cost
   that day).
8. **Very long period (`all`)** with a large day count: the stacked bar chart
   renders without errors (ECharts handles dense categories); no pagination is
   required for v1 — accept dense axis labels. If rendering proves unusable in
   manual testing, record in `docs/KNOWN_LIMITATIONS.md` rather than adding
   aggregation complexity.
9. **Custom range spanning one day**: the user picks start == end day `D`; the
   frontend sends `since = D` (midnight, ISO) and `until = D + 1 day`
   (exclusive) — valid, one day of data; extrapolation divides by 1 day
   (minimum 1 — never divide by 0). `since == until` is NOT a one-day range:
   the exclusive filter makes it empty, and the handler rejects it with 400
   (`since >= until`).
10. **Model string containing HTML/script characters** (e.g. a hand-edited
    DB row): rendered as text via the escape pattern (AC-21); no script
    execution.
11. **Period with data but zero total cost** (all models free/unpriced):
    donut and stacked bar show empty/zero states without NaN; KPI % values
